Coordination does not transfer another member's component responsibility.

| Context | Documentation convention |
|---|---|
| Shared work | Use “project team”. Record group approval only when evidence shows the team gave it. |
| Code peer review and merge | At least one other human team member must review and approve code before merge into `main` (H4). AI tools may assist the human reviewer, who must assess the changes and decide whether to approve (H5); self-review or AI review alone does not replace peer review. After review blockers are resolved and required checks pass, the human author or reviewer may merge within repository permissions/protections; substantive later code changes require renewed review. |
| AI Git/GitHub actions | Users create branches using the command supplied by the assistant; humans open and merge PRs. AI may draft an Issue, but must obtain explicit user permission for that specific Issue before creating it (H5). Identifying a need or following a workflow does not grant permission. |
| Component work | Name the member or say “responsible component member”. Existing “component owner” labels describe responsibility for that component, not ownership of the entire project. |
| Historical instruction, confirmation or execution | Name the person, date, source and exact scope. Do not turn an individual instruction into group approval. Preserve literal historical metadata where quoted, with context. |
| Teaching | Use “guidance from the COMP1884 lecturer”. Use “module leader” only where that distinct role is evidenced. A lecturer need not be a research contributor, and teaching alone does not establish supervisor appointment or approval of a specific method. |
| University alignment | Say “checked against the applicable COMP1884 assessment criteria”, identify the evidence and report remaining gaps. Do not claim university approval or full compliance from this draft. |
